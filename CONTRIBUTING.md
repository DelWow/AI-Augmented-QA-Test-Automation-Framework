# Contributing

Use Node.js 24 (`nvm use`) and install dependencies with `npm ci`. See the [README](README.md) for setup and [configuration](docs/configuration.md) for browser and environment settings.

## Making changes

Keep the API, [OpenAPI contract](app/openapi.yaml), and tests in sync. Run the affected suite while developing, then `npm run test:all` for code changes on a supported visual-baseline platform. Include test results and any checks you couldn't run in the pull request.

Use unique test users, clean up their tasks, and wait for observable state rather than adding fixed delays. Selector recovery rules need checks for rejected matches as well as successful lookups.

Before submitting, run `git diff --check` and review the diff. Generated reports, current screenshots, diffs, dependencies, and credentials should stay out of version control.

## Test assets

- **Postman:** edit `qa/postman/generate-edge-cases.js`, run `node qa/postman/generate-edge-cases.js`, and include the updated collection. Update the brief if coverage changes.
- **Cypress:** keep suggestion IDs and their documentation aligned with the specs.
- **Visual baselines:** follow the [update procedure](qa/visual/README.md). Review all four images and the manifest, then rerun comparison. Use a Chrome for Testing version that a clean runner can download.
- **AI reviews:** keep assessments separate from test verdicts and baseline approval. Cover provider responses and errors with mocks; identify live-provider checks separately in validation notes.

## CI changes

The workflow is [.github/workflows/qa.yml](.github/workflows/qa.yml). Keep action versions pinned to reviewed commit SHAs and validate workflow edits with `actionlint`. Check the hosted run after pushing, especially when changing the runner OS or visual browser version. Baselines are reviewed and updated locally, never regenerated by CI.
